# ARQOS 제품 개발 방향 (CEO Directive)

> 출처: 「Tfoi & ARQOS 핵심 제품 개발 방향 및 필수 서비스 개발 요구사항」 Ver 1.1 (2026.11, 대표이사 → 프런티어오피스 PX전략파트 · 파운드리오피스, 41쪽)
> **ARQOS 기획 · 화면 설계 · 정의서 작성 · 티켓 검토를 할 때 이 문서를 기준으로 삼는다.** 특정 고객사 요청이 아니라 로아스 제품의 기본 완성 기준이다.

## 0. 한 줄 요약

- **ARQOS는 로봇 관제 플랫폼이 아니라 산업 통합 리스크 관리 플랫폼(Integrated Industrial Risk Management Platform)이다.** 리스크를 식별 · 탐지 · 분석 · 평가 · 예측 · 대응한다
- **기술의 복잡성은 개발 조직이 감당하고, 고객에게는 단순하게.** "설비를 클릭하는 것만으로 상태와 리스크를 확인하고, 한 번 더 조작하면 재검사 요청이나 대응을 할 수 있어야 한다"
- **개발자의 일은 FAE가, FAE의 일은 고객이** 하도록 만든다 = 기술의 제품화
- ARQOS 서비스 범위는 Tfoi 기능이나 지금 가진 검사기술에 묶이면 안 된다

## 1. 기획할 때 적용하는 원칙

### 5대 핵심 원칙
| # | 원칙 | 기획에서 의미 |
|---|---|---|
| 1 | 직관성 · 1~2 Click | 핵심 정보와 일반 운영 기능은 1~2번 클릭으로 접근. **단, 비상제어 · 위험구역 진입 · 안전 설정 변경은 인증 · 승인 절차를 생략하지 않는다** |
| 2 | 운영 독립성 | 개발자 → FAE → 고객 순으로 업무 이관. 개발자가 현장 운영을 계속해야 하면 미완성 제품 |
| 3 | SI가 아닌 제품 | 고객 요구를 그대로 구현하지 않고 산업 공통 문제인지 검토해 범용 기능 + 설정 옵션으로 재정의 |
| 4 | 로봇 · HW 비종속 | Tfoi 전용 관제 SW가 아니다. Tfos, 고정형 센서, 외부 로봇까지. 서비스의 중심은 **설비(Asset) · 리스크(Risk) · 임무(Mission)** |
| 5 | 정량 · 신뢰 | 정상/이상 구분을 넘어 상태 변화와 리스크 수준을 수치와 근거로 제공 |

### UX 원칙 (1~2 Click 세부)
1. 매뉴얼 없이 이해되는 인터페이스
2. 핵심 정보 · 일반 운영 기능 1~2 Click
3. 메뉴 이동 · 중복 입력 · 반복 설정 최소화
4. 설비 · 로봇 · 이벤트 등 **객체 중심** 정보 접근
5. 상황에 따라 필요한 기능을 먼저 주는 Context-Aware UI
6. 복잡한 기술 설정은 **고급 설정 영역으로 분리**
7. 위험도 · 우선순위 순으로 중요한 정보가 먼저 보이는 화면
8. PC · 태블릿 · 모바일 일관된 경험
9. 일반 운영 기능과 안전 제어 기능을 명확히 구분

### 지양 → 지향
| 지양 | 지향 |
|---|---|
| 고객사별 소스코드 수정 | 설정 기반 서비스 구성 |
| 현장마다 신규 개발 | 표준 기능의 선택 · 조합 |
| 개발자 중심 현장 구축 | FAE 중심 현장 구축 |
| 전문인력 의존형 검사 설정 | 사용자 중심 검사 설정 |
| 고객 요구 단순 구현 | 산업 공통 문제의 제품화 |
| 사업장별 독립 시스템 | 공통 플랫폼 기반 확장 |
| 기술 중심 인터페이스 | 사용자 중심 인터페이스 |

- **PX에게**: "무엇을 개발해 줄지" 묻지 말고 표준 서비스 모델을 먼저 제시한다. 고객 요구는 범용 제품 요구사항으로 재정의한다

### PX가 기능마다 던질 7가지 질문
1. 고객이 이 기능을 왜 필요로 하는가?
2. 고객이 가장 먼저 확인해야 하는 정보는 무엇인가?
3. 이 기능에 접근하기까지 몇 번의 조작이 필요한가?
4. 별도 교육 없이 쓸 수 있는가?
5. 기존 업무보다 시간과 절차가 줄어드는가?
6. 다른 산업 · 사업장에도 똑같이 적용할 수 있는가?
7. 산업 리스크 관리라는 ARQOS의 본질에 기여하는가?

## 2. ARQOS 제품 방향

### 리스크 관점
- **탐지로 끝나지 않는다**: 탐지 → 평가 → 대응 → 해소 확인의 Closed-Loop
- 리스크는 개별로 존재하지 않는다: 상관관계 · 파급효과를 분석하는 방향. 새 검사기술 · 외부 시스템이 붙어도 근본 구조가 바뀌지 않게 설계
- **10대 리스크 영역** (당장 모두 진단하라는 뜻이 아니라 확장 가능한 구조로 설계하라는 뜻)
  Equipment · Process · Human Safety · Environmental · Fire & Explosion · Infrastructure · Operational · Security · Compliance · Business Continuity

### 핵심 서비스 (5장)
| 번호 | 항목 | 요점 |
|---|---|---|
| 5.1 | 설비 디지털 자산화 | 모든 설비 · 배관 · 구조물 · 공간에 **Unique Asset ID**. 사업장 > 건물 > 층 > 구역 > 설비 > 부품 계층. 3D 객체 매핑, 고객사 자산관리번호 연계. 진단 · 이력 · 위험도 · 재검사 · 보고서가 **설비 중심으로 연결** |
| 5.2 | Digital Twin 기반 임무 설계 | 1차: 3D 맵에서 웨이포인트 수동 설계 · 시뮬레이션 · 저장/복제. 2차: 설비 선택 → 검사 임무 · 지점 · 경로 자동 생성, 사용자 검토 · 승인. **고객은 경로를 설계하지 않고, 어떤 설비를 언제 어떤 방식으로 검사할지만 고른다** |
| 5.3 | 영역 기반 미션 | 맵 위 Drag & Drop · Polygon으로 진단 · 순찰 · 위험 · 금지구역 설정, 영역 내 설비 자동 식별 |
| 5.4 | 로봇 비종속 Fleet | 임무 · 경로 · 로봇 독립 관리. Mission Pool → Scheduler가 최적 로봇 자동 배정. 장애 시 대체 배정, 충돌 방지, 긴급 임무 중단 · 재개 |
| 5.5 | 고객 주도 설정 · 연동 | 검사 항목 · 주기 · 알림 조건, 이상 판단 기준, 이메일 · SMS · 메신저 알림, REST · MQTT · OPC UA · Webhook |
| 5.6 | 12개 운영 모드 | 3D Digital Twin · 2D Map · Asset Monitoring · Risk Monitoring · Fleet Management · AI Diagnostics · EHS Monitoring · Live Monitoring · Executive Dashboard · Multi-Site · Lite(VDI · 저사양) · Emergency |
| 5.7 | 사용자 정의 대시보드 | 위젯 · Drag & Drop · 사용자별 레이아웃 저장 · 역할별 템플릿 · 즐겨찾기 · 다중 모니터 · 반응형. **화면 변경을 위해 로아스에 개발을 요청하지 않게** |
| 5.8 | 설비 원격 재검사 | 설비 선택만으로 즉시 재검사, 가용 로봇 자동 배정, 이전 · 신규 결과 비교, 조치 전후 리스크 변화 |
| 5.9 | 현장 작업자 원격 소통 | 양방향 음성, Tfoi 카메라 영상, TTS · 다국어, 비상 우선 통신 |
| 5.10 | Tfoi 등록 · 제거 간소화 | QR · 시리얼 등록, 구성 자동 인식, 맵 · 설정 자동 배포, 교체 시 설정 승계 |
| 5.11 | 비상 대응 모드 | 일반 임무 중단, 위험 위치 · 영향 범위 시각화, 대피 안내, 소방 · EHS 연계, 관리자 승인 기반 복귀. **법정 소방 · 방재 시스템을 대체하지 않고 보조** |
| 5.12 | 자동 보고서 | 일 · 주 · 월 · 분기, 사업장 · 구역 · 설비별, 수행률 · 누락, 사용자 정의 템플릿, PDF · Excel, 담당자 자동 전달. **엑셀로 다시 정리하지 않게** |
| 5.13 | 설비 히스토리 · 추이 | 특정 시점이 아닌 장기 변화. 기간 비교, Baseline 대비, 정비 전후, 반복 이상 패턴 |
| 5.14 | 정량 진단 | 음향 · 누설 · 열화상 · 비전 · OCR · 설비 상태(Health Index, Anomaly Score) · 리스크(Risk Score/Level/Trend). **AI 신뢰도(Confidence) ≠ 리스크 심각도.** 수치마다 측정 방법 · 단위 · 정확도 · 판단 기준 · 적용 한계 정의 |

### 리스크 엔진 (9장)
- 9.1 리스크 분류 · 등록: 산업 · 설비 · 공정별 분류체계, 사업장별 잠재 위험요소, 리스크별 검사기술 · 대응 연결, 고객사별 판단 기준
- 9.2 멀티모달 이벤트 상관: 같은 설비의 이상음 + 온도 상승 + 부하 증가를 하나의 복합 리스크로
- 9.3 Risk Score: 설비 · 구역 · 공정별 점수, 가능성 × 영향도 Matrix, 사업장 Risk Index, 설비 중요도 반영, 미조치 · 지연 현황, 사업장 간 비교
- 9.4 3D Risk Heatmap: 공간 자체가 리스크를 보여 주고, 객체 선택 시 대응 기능 즉시 제공
- 9.5 Closed-Loop 워크플로: 자동 통보 → 우선순위 → 재검사 요청 → 대응 가이드 → 담당 · 기한 → 조치 기록 → **해소 확인** → 재등록 → 감사 이력
- 9.6 Open Data: Tfos, 고정형 센서, CCTV, IoT, 외부 로봇, PLC · SCADA · DCS · MES · CMMS · EAM. **공통 자산 데이터 모델 · 이벤트 데이터 모델 · 표준 API를 초기부터 설계**

### 모바일 (7장)
- FAE 앱: Tfoi 등록 · 네트워크, SLAM · 맵 편집, 주행 테스트, 검사 위치 · 조건 설정, HW · SW 상태 진단, 로그 · 업데이트 · 롤백, 구축 체크리스트, 오프라인 지원
- 고객 앱: 사업장 리스크 현황, 설비 상태 · 진단 결과, Tfoi 위치 · 상태, 이상 Push, 영상 · 음향 · 열화상 확인, 원격 재검사, 이력 · 공유, 조치 · 완료 처리, 보고서, 비상 알림, 복수 사업장 · 다국어
- 목적 · 권한은 구분하되 공통 API · 백엔드 사용

### 운영 신뢰성 (10장, 부록)
- 수백 개 사업장을 **방문 없이** 운영: 자율 장애 복구, OTA, Health Monitoring, 원격 로그, 통신 단절 시 저장 후 동기화, 검사 데이터 유효성, 보안, 사업장 설정 템플릿 복제, 온프레미스 · 폐쇄망
- Tfoi 유지보수 5단계: Monitoring → Remote Recovery(ARQOS 원격 복구) → Autonomous Recovery → Preventive(마일리지 기반) → Predictive(AI)
- 로봇 자체의 리스크도 관리: 구동계 · 배터리 · 센서 · 주행 · 리프트 · 컴퓨팅 · 네트워크 · 충전 · SW 상태, Robot Health Dashboard, 표준 Error · Fault Code
- **안전 계통 장애는 검증 전 자동 주행 재개 금지**

### 그 밖의 영역 (기획 시 연계만 인지)
- 자율주행(4장): 조합형 멀티 주행, FAE 중심 주행 설정(GUI · 프리셋 · 파라미터, 소스 수정 없이), SLAM 간소화(FAE가 태블릿으로 맵 구축), 비전 융합, 실외 · 악천후. 완료 기준은 "FAE가 개발자 없이 맵을 구축 · 검증할 수 있는가"
- 하드웨어(6장): Tfoi 제품군(Compact · Standard · Heavy-Duty · Hybrid · Outdoor · Ex)이 달라도 ARQOS 연동 · 검사 데이터 구조 · 운영체계는 공통. 온보드 HMI, 언어모델 기반 소통
- 인증(6.7~6.9): Compliance by Design. 방폭 · 해외 인증은 리드타임이 길어 초기부터 병행
- 검사기술(8장): 검사기술파트는 "검사 도구를 만드는 조직". 통합 멀티모달 검사 SW, 음향 표준화, No-Code 비전 AI 학습, 정량 열화상(Point · Line · Area · Polygon ROI). 검사 대상 · 성능 · 최소 탐지 수준 · 적용 한계 등 10개 항목을 정량 정의해야 PX가 서비스를 정확히 기획할 수 있다

## 3. 조직 역할

- **PX전략파트 = 정의(Define)**: 제품 · 서비스의 완성된 모습을 정의하고 기술을 고객 가치로 바꾼다. 요구사항 수집 · 화면 디자인 조직이 아니다
  - 산출물: PRD, Persona & User Role, Industrial Use Case, User Journey & Workflow, Information Architecture, One-Two Click UX Flow, Service Configuration Model, Wireframe & Prototype, Product Acceptance Criteria, Usability Test & Feedback
- 파운드리오피스 = 구현(Build): 요구사항보다 나은 대안이 있으면 제시
- FAE파트 = 검증(Validate): 현장 경험을 데이터 · 요구사항으로 정리해 PX · 파운드리로 환류

## 5. 완료 기준

### KPI 제안 목표 (초기 제안값, 측정 방법 · 최종값은 추후 확정)
- 사용성: 핵심 리스크 정보 접근 1~2 Click / 일반 재검사 요청 1~2 Click / 핵심 업무 성공률 95% 이상
- 현장 구축: 표준 사업장 개발자 개입 0건 / SLAM · 주행 최적화 소요시간 50% 단축
- 운영: 신규 로봇 등록 5분 이내 / 정기 보고서 자동 생성 100% / 일반 설정 시 코드 수정 0건
- 기타: 임무 성공률 99%, 유효 검사 데이터 99%, 검사 누락 1% 이하, 자율 복구율 95%, 가용률 99.9%, 필수 안전 시험 100% 통과

### Definition of Done (개별 기능마다 11개 항목 정의)
Why · What · Who · How · When · Dependency · KPI · Validation · Acceptance(PX · QA 승인 기준) · Documentation · Deployment
- 완료 = **실제 현장에서 FAE와 고객이 독립적으로 쓸 수 있을 때.** "내 환경에서 작동한다"는 완료가 아니다
- **UX from Day One**: 기능 개발 이후에 UI를 고민하지 않는다

## 6. 최종 지향점 (기존 → 지향)

로봇 관제 → 산업 리스크 통합관리 / 설비 이상 탐지 → 리스크 평가 · 대응 / 개별 센서 데이터 → 멀티모달 통합 인텔리전스 / 정상 · 이상 구분 → 정량적 상태 · 위험도 / 로봇 중심 임무 → 설비 · 리스크 중심 임무 / 고정형 관제 화면 → 사용자 중심 서비스 환경 / 복잡한 조작 → 1~2 Click / 개발자 중심 구축 → FAE 중심 구축 / 전문인력 검사 설정 → 고객 주도 검사 / 고객사별 개발 → 범용 제품 · 표준 서비스 / 단일 로봇 → 공통 플랫폼 제품군 / 이상 후 알림 → 예방 · 대응 · 조치 · 검증 / 현장 방문 지원 → 원격 운영 · 유지보수

궁극 목적: **안전성 · 설비 신뢰성 · 생산성 · 사업 연속성**

## 7. 기획 체크리스트 (작업할 때 이렇게 쓴다)

ARQOS 기획 · 화면 · 정의서 · 티켓을 다룰 때 아래를 확인하고, 어긋나면 사용자에게 짚어 준다.

- [ ] 정보의 중심이 **로봇이 아니라 설비 · 리스크 · 임무**인가? (Asset ID 기준으로 이력 · 진단 · 보고서가 연결되는가)
- [ ] 핵심 정보 확인 · 일반 운영(재검사 등)이 **1~2 Click**인가? 안전 관련 기능은 인증 · 승인 절차를 지켰는가?
- [ ] 탐지에서 끝나지 않고 **평가 → 대응 → 해소 확인**까지 흐름이 이어지는가?
- [ ] 특정 고객사 요구를 그대로 반영한 것은 아닌가? **설정 옵션 · 표준 기능**으로 일반화했는가?
- [ ] 고객 · FAE가 **개발 요청 없이** 설정 · 변경할 수 있는가? 복잡한 설정은 고급 설정으로 분리했는가?
- [ ] Tfoi 전용으로 굳어지지 않았는가? 다른 로봇 · 센서 · 외부 시스템이 붙어도 구조가 유지되는가?
- [ ] 수치를 보여 줄 때 단위 · 기준 · 근거가 있는가? AI 신뢰도를 위험도로 쓰지 않았는가?
- [ ] 위험도 · 우선순위 순으로 중요한 정보가 먼저 보이는가?
- [ ] PC · 태블릿 · 모바일에서 일관되게 쓸 수 있는가?
- [ ] 7가지 질문(Q1~Q7)에 답할 수 있는가? DoD 11개 항목을 채울 수 있는가?

> 단, 현재 진행 중인 v2.2 · 고객사 대응 건은 기존 결정(예: "v3에서 대시보드 구조가 바뀔 예정이므로 공수는 최소로")을 따른다. 이 방향은 **v3 기획과 신규 기능 기획의 기준**으로 우선 적용하고, 기존 결정과 충돌하면 바꾸지 말고 사용자에게 먼저 짚는다.
